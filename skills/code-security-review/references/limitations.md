# Limitations: what this skill does not enforce

This is a plain Agent Skill. It runs on any host that loads skills, and in exchange it
gives up the controls an agent harness can enforce: per-agent tool allowlists, write
confinement to one folder, a deny-by-default shell, hooks, model pinning and a
reasoning-effort setting. What the **scripts** enforce is still enforced: the run-directory
gate, the snapshot, the extractor's accounting, the candidate gate, the citation and schema
checks, the arbitration gate, the report gate, the ledger's refusals. What the **harness**
used to enforce is now convention, and a model or a hostile input can ignore a convention.

The table says, row by row, what holds and what does not. A reader of any report from this
skill should be able to see what was and was not protected for that run. The hardened,
harness-specific variants still exist in the frozen source repositories.

## How to read "Strength now"

| Label | Meaning |
|---|---|
| **kept** | enforced by a script on every host |
| **same as before** | it was always a prose rule, and still is |
| **weakened, recorded** | enforced less strongly than before, and the evidence level is written into the run output |
| **detect-only** | a violation can be noticed after the fact, not prevented |
| **host-dependent, recorded** | depends on what the host provides; the result is recorded per unit |
| **lost** | nothing enforces it any more; it is a convention |

| Text in the repository is data, never instructions | prose in the agent profiles | prose: a STOP rule in SKILL.md and a sentence in every dispatch prompt; a role that meets text addressed to a reviewing tool copies it into the manifest's `suspicious_content` (`ingest` does it for a validator's `addressed to the review:` observation), the report gate counts it and the report has to name it; and the part of a brief the script writes does not carry a folder name the repository chose unless it is one plain printable line (`unit-task` counts the leave-outs it does not print; the sweep's and the summary's lists escape the names), so a folder called `x<line break>==== TASK ...` cannot add lines to a validator's brief | **same as before** (always prose, plus a record). Nothing stops a model from obeying a planted instruction, and the record holds only what a role noticed and copied. ## What every run summary must say

`review_run.py summary` and the report print, in this order:

1. the dispatch mode of each unit (`subagent` or `inline`), the models when recorded, and
   how many units were recorded, and how many launches did not deliver and were repeated
   (`dispatch-record --attempt-failed`); for any unit that ran inline, was never recorded,
   was never closed or delivered nothing, that independence is weaker or unknown;
2. the approval gates: the scope choice and the cut are the person's and are quoted; the
   ledger review is the person's and the summary says how many decisions are recorded for
   the run (none yet is a normal answer); the upstream check, when run, carries the
   evidence level `tty`, and the summary says so, or says that no terminal confirmation is
   recorded;
3. what the scanner skipped as its own tooling (`tooling_skipped`), what is in the scratch
   folder, and what changed outside the run directory;
4. the sentence "Not enforced on a plain skill install: see" and the absolute path of this
   copy's `references/limitations.md`, so the reader can find this file from wherever they are.

`summary` ends with all of this as `tellThePerson`, a list of sentences for the orchestrator
to say as they stand.

## Known limits of the analysis

These are about what the pipeline can know. They hold on every host and were true of the
original; nothing here claims to have closed them.

- **The ranking is the load-bearing limitation.** The pipeline extracts every function and
  adjudicates a few hundred. Which few hundred is decided by the scorer: `llm-triage` (a
  general model's four-way call, ordered inside each bucket by the `rules` backend) or
  `rules` (a capped, weighted sum of rule hits, reachability and churn, less penalties for
  test, generated and sample trees). Either is an ordering and neither is a model of
  exploitability. A vulnerable function the ordering does not favour ranks low, and a run
  that never reaches it reports nothing about it. That is why `operating-point.json`
  carries `not_selected_is_not_a_clean_bill` as a literal field and why the report gate
  will not let the count be printed without it. A fine-tuned function-level classifier
  closes the gap only within the window it was trained on.
- **`LOG-TRI` is a model's say-so, used only to decide where a validator looks.** Under
  `llm-triage`, a selected function that no rule matched is reviewed only when the triage
  model rated it `high`: stage 3 then gives it one `LOG-TRI` candidate, and a logic-flaws
  validator reads the whole function against four absent-control checklists (is the caller
  authenticated, may it act on this object, is the origin of the input verified, is a
  one-time value checked). Before 0.1.3 such a function was listed under
  `selected_without_candidate` and read by nothing, so a handler with a neutral name and an
  *absent* check (a webhook that never verifies its signature, a delete with no owner check)
  never reached a validator at all. Nothing checks the verdict. The triage worker read the
  function's own text, comments and strings included, so text written to steer a reviewer
  steers it too: a planted line can talk a vulnerable function down to `medium`, where it
  is again listed as selected without a candidate and unexamined, or talk decoys up to
  `high`, which costs one validator call per up to five decoys in a file. The cut's rows
  show those calls before the person chooses, and `triage_degenerate` fires when one band
  holds 95% of the verdicts; neither proves that a verdict fits its function. A flood can
  also price the real ones out of the cut: `--triage-candidates-max N` keeps the first N
  owed functions by rank, which among functions no rule matched is the rules tie-break over
  zero hits and then the function id, a fixed order and not a judgement, so a ceiling can
  drop the vulnerable handler and keep the decoys. On a corpus of 50 or more functions, when
  five or more are owed and they are over 5% of the corpus or more than half of a row's
  calls, the table adds a note to open a few verdict files before paying.
  The verdict is not evidence: the candidate record and its packet carry none of its
  sentence, CWE or line (the record's `score` and `rank` are the position every candidate
  carries), the default verdict is still `NOT_VULNERABLE`, every citation is re-read, and
  the candidate gate (I8) refuses a `LOG-TRI` that no recorded `high` verdict, rule-hit-free
  function and selected rank owe. But the verdict files stay on disk under `scores/triage/`,
  and a validator that goes looking can read them, which its role file forbids and nothing
  enforces (the "Peer independence" row above). The suspicious-content record scans a
  candidate's anchor line and hints, not the body, so an injection in the body that steered
  the triage is in `suspicious_content` only if a validator copies it; the triage worker's
  `explanation` (rule 2 of its role file) is the only trace of it. The verdict files are
  this run's only as far as the run-directory check can vouch: in a tree git does not track,
  a shipped `scores/` can plant or remove them. With the `rules` backend (it records no
  verdict), with `--no-triage-candidates`, and in a single-function check, nothing is
  derived and a function no rule matches has no candidate. A function with any rule hit gets
  that rule's validator and not this pass: a delete handler whose body calls `remove(` is
  checked for path traversal (`INJ-004`), not for a missing owner check. A C, C++ or Rust
  function reviewed under `LOG-TRI` gets no `MEM-WFS` memory pass. Test-tree, generated and
  vendored code is left out; examples and docs are not (the exposure ceiling caps them at
  `low`). A byte-identical copy reviewed under another rule is not held to the same answer
  as its `LOG-TRI` twin (the rule is part of the twin identity); the status names such a
  copy. The arbiter reads every `FP-NOT-SECURITY` dismissal (an absence code), so a
  `LOG-TRI` closed as "nothing here to protect" costs an arbiter read as well.
- **Arbitration reduces fabricated and misrated findings; it does not make the pipeline
  sound.** An arbiter that shares a model with the validators it audits shares their blind
  spots, and no adjudication recovers a vulnerability the ranking never surfaced. The
  dismissal-sample overturn rate is the arbiter disagreeing with a few dismissals nothing
  else queued, not a false-negative rate; 0 overturned of 5 is consistent with any rate up
  to 45%, and it takes 29 draws with none overturned to bound the rate under 0.10. Nothing
  in this pipeline measures recall.
- **No call graph is claimed.** Function pointers, vtables, dispatch tables, macros and
  reflection read as unreferenced unless `build_graph.py` binds the assignment, and the
  validators' caller search is text search. It does not understand a build configuration
  that is not in the tree, and it does not replace fuzzing, sanitizers or a human audit.
  `NEEDS_HUMAN_REVIEW` is a real verdict and will be a meaningful share of the output on any
  nontrivial codebase: those are the ones to read first.
- **Twins are byte-identical bodies, nothing looser.** A copy that differs by a comment or
  one patched line is a different function to every stage.
- **The static-analyzer join is location-based.** Agreement reorders the queue and nothing
  else.
- **The ledger measures the pipeline, and only on what it showed the reviewer.** A rejection
  rate says nothing about the functions below the operating point.
- **Native Windows is not supported: use WSL2 or a Linux container.** Nothing refuses to
  start, but the roles' single-quoted `rg` patterns assume a POSIX shell, the ledger has no
  lock (`fcntl` is POSIX-only, so two writers at once can be given the same `DEC-` or
  `SUP-` id), and the snapshot's link defences are weaker without `O_NOFOLLOW` and
  `dir_fd`. Only Linux has been run, so nothing is claimed for macOS or Windows. The
  selftests skip, name and count the cases that need a symbolic link, a named
  pipe or a unix socket where the platform cannot make one (checked on Linux with those calls made
  to fail, the way Windows without Developer Mode fails them; not on Windows).

`references/pipeline-contract-stage1.md` and its siblings are the normative description of
every artifact, schema and refusal named above.
